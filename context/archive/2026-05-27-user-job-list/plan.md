# User Job List Implementation Plan

## Overview

Implement a `GET /jobs` endpoint that returns the authenticated user's discovered job listings with pagination. Users can view their complete job history (both evaluated and unevaluated jobs) with match scores included when available. This endpoint forms the backbone of the results dashboard (Stream B, S-08 in roadmap).

## Current State Analysis

- **API Infrastructure:** FastAPI server (F-01) with JWT authentication middleware in place. Auth dependency `get_current_user` extracts user_id from token and validates user existence.
- **Database:** PostgreSQL with Job and Evaluation tables; Job has user_id FK for isolation; discovered_at timestamp for ordering. Evaluation table links to Job via job_id and stores match_score.
- **Repositories:** `JobRepository.get_by_user()` already handles pagination with limit/offset; `EvaluationRepository.get_by_job_id()` retrieves single evaluation; no method yet for LEFT OUTER JOIN (Job + score).
- **Response patterns:** Pydantic BaseModel schemas used for validation; endpoints inject user via auth dependency; response dicts use standard REST field names.
- **User decisions:** Conservative pagination (default 10, max 50); response includes id, title, company, url, and match_score (nullable). No filtering, fixed DESC sort by discovered_at.

### Key Discoveries:

- Job model stores discovered_at and created_at; S-06 workflow sets discovered_at when job is first created.
- Evaluation table is sparse initially — jobs created by S-04 (scout) but not evaluated until S-06 workflow runs and Orchestrator scores them. Match_score is null for unevaluated jobs.
- User scoping is enforced at DB level (FK constraints) and query level (WHERE user_id = ?). Auth dependency ensures request JWT contains valid user_id.
- Pagination pattern established: request `?page=1&page_size=10` → offset = (page - 1) * page_size; response includes page, total_count, page_size for pagination UI.

## Desired End State

After implementation:
- Endpoint `GET /api/jobs` is live and authenticated
- Returns paginated job list for authenticated user (default 10 per page, max 50)
- Each job includes: id, title, company, url, and match_score (null if not yet evaluated)
- Response always includes pagination metadata: page, total_count, page_size
- Sorting is fixed to discovered_at DESC (newest first)
- Invalid pagination parameters are clamped to valid range (page < 1 → page 1; offset > max → last page)
- Empty result set returns 200 OK with empty jobs array, not 404 or 204
- Multi-user isolation is validated: user can only see their own jobs
- API documentation auto-generated by FastAPI OpenAPI schema

**Verification:** User can call endpoint, receive paginated results, pagination works across multiple pages, match_scores appear when jobs are evaluated, unauthenticated requests return 401.

## What We're NOT Doing

- No filtering, searching, or advanced query parameters (keep endpoint simple)
- No sorting options beyond discovered_at DESC (UI can sort client-side if needed)
- No evaluation summaries in job list (match_score only; tailor_summary is S-09's responsibility)
- No per-job caching or ETag headers (added complexity for local MVP deployment)
- No rate limiting (Phase 2 feature per roadmap)
- No response compression or streaming (pagination handles scale)

## Implementation Approach

1. **Extend JobRepository** with a method `get_jobs_with_scores()` that performs LEFT OUTER JOIN with Evaluation table, returning Job + optional match_score tuples. This avoids N+1 queries and keeps DB logic clean.

2. **Create response schemas** in `src/api/schemas.py`:
   - `JobListItemResponse`: id, title, company, url, match_score (nullable float)
   - `GetJobsResponse`: page, total_count, page_size, jobs array

3. **Add endpoint** in new file `src/api/routes/jobs.py`:
   - `GET /api/jobs?page=1&page_size=10`
   - Accepts page and page_size query params (with validation)
   - Requires auth via `Depends(get_current_user)`
   - Calls `JobRepository.get_jobs_with_scores()` with pagination
   - Returns `GetJobsResponse` with status 200

4. **Register router** in `src/api/main.py` to include the new routes

5. **Add unit tests** in `tests/test_routes_jobs.py`:
   - Test successful retrieval with paginated results
   - Test sorting by discovered_at (newest first)
   - Test optional match_score (present vs null)
   - Test pagination bounds (clamping, last page, empty result)
   - Test multi-user isolation (user can't see other users' jobs)
   - Test auth requirement (401 without token)

## Critical Implementation Details

**LEFT OUTER JOIN for match_score:** The query must use LEFT OUTER JOIN (not INNER) so jobs without evaluations still appear with match_score=null. Pattern:
```
SELECT Job, Evaluation FROM Job
LEFT OUTER JOIN Evaluation ON (Evaluation.job_id = Job.id AND Evaluation.user_id = ?)
WHERE Job.user_id = ?
ORDER BY Job.discovered_at DESC
```

**Pagination offset calculation:** `offset = (page - 1) * page_size`. Must clamp page to [1, ceil(total_count / page_size)]; clamping avoids 400 errors for off-by-one mistakes in frontend.

**Empty page handling:** If page is clamped to beyond max, return empty jobs array but keep metadata correct (e.g., requesting page 999 with 100 total jobs returns page 10, empty jobs array, total_count 100).

**File**: `src/db/repositories.py`

**Intent**: Add a new static method that retrieves jobs for a user with optional match_score from the Evaluation table. This method handles the LEFT OUTER JOIN so the API endpoint doesn't need raw SQL. Returns a list of tuples: (Job object, match_score or None).

**Contract**: 
```python
@staticmethod
async def get_jobs_with_scores(
    session: AsyncSession, user_id: UUID, limit: int = 20, offset: int = 0
) -> List[tuple[Job, Optional[float]]]:
    """Retrieve jobs with optional match scores for a user."""
```

The method:
- Queries Job + LEFT OUTER JOIN Evaluation
- Filters WHERE Job.user_id = user_id
- Orders BY Job.discovered_at DESC
- Applies LIMIT and OFFSET
- Returns list of (Job, match_score_or_none) tuples for easy response mapping

## Phase 2: Endpoint Implementation

### Overview

Create GET /api/jobs endpoint with pagination logic, pagination parameter clamping, and auth dependency injection.

### Changes Required:

#### 1. New route file: jobs.py

**File**: `src/api/routes/jobs.py`

**Intent**: Implement the GET /api/jobs endpoint with pagination query parameters, authentication, and response building. Handles pagination parameter validation (clamping) and calls repository.

**Contract**: 
- `@router.get("/jobs")` with prefix `/api` (full path: `/api/jobs`)
- Query params: `page: int = Query(1, ge=1)`, `page_size: int = Query(10, ge=1, le=50)`
- Auth: `user: User = Depends(get_current_user)`
- DB: `session: AsyncSession = Depends(get_db)`
- Returns: `GetJobsResponse` dict
- Status: 200 OK (always, even for empty results)

Logic flow:
1. Extract page, page_size from query params
2. Clamp page if needed: max_page = ceil(total_count / page_size); if page > max_page, use max_page
3. Calculate offset = (page - 1) * page_size
4. Call `JobRepository.get_jobs_with_scores(session, user.id, limit=page_size, offset=offset)`
5. Call `JobRepository.count_by_user(session, user.id)` for total_count
6. Build response list: map each (Job, score) tuple to JobListItemResponse
7. Return GetJobsResponse with page, total_count, page_size, jobs

#### 2. Register router in main.py

**File**: `src/api/main.py`

**Intent**: Import the new jobs router and register it with the FastAPI app so the endpoint is live.

**Contract**: 
Add import: `from src.api.routes import jobs` (line ~14)
Add registration: `app.include_router(jobs.router)` (line ~135, after other routers)

## Performance Considerations

**Database query efficiency:**
- LEFT OUTER JOIN with WHERE (user_id) + ORDER BY (discovered_at) uses existing indexes (ix_jobs_user_id, ix_jobs_user_id on evaluations).
- LIMIT + OFFSET are efficient for pagination (no sorting overhead).
- Two queries: one for jobs (with optional score), one for count. Alternative: single COUNT(*) query or use window functions. Current approach is acceptable for local MVP; Scale Phase 2 if needed.

**Response payload:**
- Default page_size=10 → ~5-10 KB response (id, title, company, url, null/float score).
- Max page_size=50 → ~25-50 KB response; acceptable for local deployment.

**Caching strategy:**
- No client-side caching (user jobs change frequently as workflow runs).
- Database handles row-level caching at connection pool.
